# 跨层思维指南

> **用途**：在实现跨层功能之前，理清测试框架各层之间的数据流和契约。

---

## 核心问题

**大多数 Bug 发生在层边界**，而非层内。

本项目的层结构：

```
FMF 元数据层          → 定义测试范围、依赖、环境要求
    ↓
Shell 测试层          → Beakerlib 测试脚本，调用被测工具
    ↓
测试库层（lib/）      → 共享函数、环境检查
    ↓
CI 流水线层           → GitHub Actions 调度、Runner 管理
    ↓
资源层（CloudPods）   → 虚拟机/K8s 集群管理
```

---

## 实现跨层功能前

### 第一步：绘制数据流

```
FMF → 测试发现 → 环境准备 → 测试执行 → 结果收集 → CI 报告
```

对于每个箭头，问：
- 数据是什么格式？
- 什么可能出错？
- 谁负责校验？

### 第二步：识别边界

| 边界 | 常见问题 |
|------|----------|
| FMF ↔ 测试脚本 | 定义了依赖但脚本未安装；架构过滤不一致 |
| 测试脚本 ↔ lib/ | 共享函数签名变化后调用方未更新 |
| 测试 ↔ CI | 环境变量缺失；Runner 架构不匹配 |
| CI ↔ CloudPods | 资源未正确释放；凭证过期 |

### 第三步：定义契约

对于每个边界：
- 输入格式是什么？（FMF YAML 结构、环境变量名）
- 输出格式是什么？（TAP 结果、JSON 汇总）
- 可能的错误有哪些？（超时、资源不足、依赖缺失）

---

## 常见跨层错误

### 错误 1：环境变量隐式依赖

**坏做法**：测试脚本直接使用 CI 注入的环境变量

**好做法**：在 `lib/` 中提供统一的配置读取函数，附带默认值和校验

### 错误 2：FMF 元数据与实际测试不一致

**坏做法**：FMF 声明 `require: [packageA]`，但测试脚本实际依赖 `packageB`

**好做法**：单元测试 `test_fmf_metadata.py` 会捕获此类不一致，编写前先运行验证

### 错误 3：CI 逻辑耦合测试内容

**坏做法**：CI workflow 中硬编码测试包列表

**好做法**：CI 通过 FMF 发现测试，包列表在 FMF 元数据中维护

### 错误 4：忽略了架构差异

**坏做法**：假设所有环境都是 RISC-V

**好做法**：在 FMF 中使用 `adjust` 进行架构适配，在脚本中使用 `uname -m` 判断

## 跨层功能检查清单

**实现前**：
- [ ] 是否理清了完整的执行流程？
- [ ] 是否识别了所有层边界？
- [ ] 是否定义了每层的输入/输出？
- [ ] 是否确定了校验位置？

**实现后**：
- [ ] 是否测试了边缘情况（空值、缺失、超时）？
- [ ] 是否验证了每个边界的错误处理？
- [ ] 是否检查了跨架构兼容性（x86_64 ↔ RISC-V）？
- [ ] 是否检查了 CI 环境与本地环境的一致性？
